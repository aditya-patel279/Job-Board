What is E2E testing and why does it matter?

There are three levels of automated testing, and they form a pyramid. Unit tests test a single function in isolation — fast, cheap, and plentiful. Integration tests test how two or more modules work together. End-to-End (E2E) tests test the entire application from a user's perspective — they open a real browser, click real buttons, and check real results.

E2E tests are the most expensive to write and run, but they give you the highest confidence that your app actually works. A unit test can pass while the whole login flow is broken. An E2E test will always catch that.

Without E2E tests
  • Unit tests pass, but login is broken in production
  • A CSS change moves a button off-screen — unnoticed
  • Manual QA takes hours before every release
  • Bugs found by real users, not your team
With E2E tests
  • Full user flows tested on every code push
  • Broken UI caught in CI before it ships
  • Regression bugs surface immediately
  • Confidence to refactor without fear
Why Playwright over alternatives?

The two main E2E tools you'll hear about are Cypress and Playwright. Both are excellent, but Playwright has some important advantages:

Cypress limitations
  • Only runs in Chromium by default
  • Cannot test across multiple browser tabs
  • Runs inside the browser (limited network control)
  • No built-in support for multiple user sessions
Playwright advantages
  • Chrome, Firefox, and Safari in one config
  • Multiple tabs and contexts natively supported
  • Full network interception with page.route()
  • Multiple users in parallel — perfect for HireBoard
Playwright's secret weapon — auto-waiting. Every action (click, fill, expect) automatically waits for the element to be ready. You never write sleep(2000) or waitFor — Playwright figures it out. This is why Playwright tests are so much less "flaky" than older tools.
Understanding the config file

The playwright.config.ts file is the global remote control for all your tests. You set it up once and every test inherits these settings automatically.

🏢 In HireBoard's config
We set fullyParallel: false because our tests share localStorage — if two tests ran at the same time they'd overwrite each other's login state. We also set workers: 1 in CI for the same reason. In a real app with a database, you'd run each test in an isolated DB transaction and enable full parallelism.
The anatomy of a test

Every Playwright test has four phases: Arrange (set up the state), Act (perform actions), Assert (check the result), and optionally Cleanup. You'll see this pattern in every test file.

Generic test anatomy Concept
import { test, expect } from '@playwright/test'; test('descriptive name of what this test proves', async ({ page }) => { // ── ARRANGE: set up the state ────────────────────────────── await page.goto('/login'); // ── ACT: interact with the UI ────────────────────────────── await page.getByTestId('email-input').fill('user@example.com'); await page.getByTestId('password-input').fill('password123'); await page.getByTestId('login-submit').click(); // ── ASSERT: verify the expected outcome ──────────────────── await expect(page).toHaveURL(/dashboard/); await expect(page.getByTestId('nav-user-name')).toBeVisible(); });
Choosing the right locator

A locator is how Playwright finds an element on the page. Choosing the right one is one of the most important skills in automation — bad locators make tests brittle and break every time the UI changes.

The golden rule: Prefer locators that reflect how a user sees the page, not how a developer built it. A user clicks "Submit", not div.btn-wrapper > button:nth-child(2).
Locator hierarchy — best to worst Concept
// ✅ BEST: data-testid — explicit, stable, immune to visual changes page.getByTestId('login-submit') // ✅ GREAT: semantic role + name — mirrors how screen readers see the page page.getByRole('button', { name: 'Sign in' }) page.getByRole('textbox', { name: 'Email' }) // ✅ GOOD: label — works for inputs with a <label> element page.getByLabel('Email address') // ✅ OK: visible text — fragile if text changes, but readable page.getByText('Submit application') // ⚠️ AVOID: CSS selectors — breaks when devs refactor class names page.locator('.btn-primary.submit-btn') // ❌ NEVER: XPath or nth-child — extremely brittle page.locator('xpath=//div[2]/button[1]') page.locator('button:nth-child(3)')
🏢 How HireBoard uses data-testid
Every interactive element in HireBoard has a data-testid attribute set directly in the React JSX. For example, in AuthPages.tsx: <input data-testid="email-input" /> and <button data-testid="login-submit">. This means even if we rename a CSS class or restructure the DOM, the test locator never breaks. This is the industry standard approach.
The most important assertions

Assertions are what make a test a test. Without them, you're just clicking around. Here are the ones you'll use constantly:

Core assertion cheatsheet Concept
// URL assertions await expect(page).toHaveURL(/dashboard/); // regex match await expect(page).toHaveURL('/#/employer/dashboard'); // exact match // Visibility await expect(locator).toBeVisible(); await expect(locator).not.toBeVisible(); await expect(locator).toBeHidden(); // Text content await expect(locator).toHaveText('Exact text'); await expect(locator).toContainText('partial text'); await expect(locator).not.toHaveText('Wrong text'); // Form inputs await expect(locator).toHaveValue('expected input value'); await expect(locator).toBeEnabled(); await expect(locator).toBeDisabled(); await expect(locator).toBeChecked(); // CSS classes (useful for active states, toggle buttons) await expect(locator).toHaveClass(/active/); await expect(locator).not.toHaveClass(/active/); // Attributes await expect(locator).toHaveAttribute('aria-pressed', 'true'); // Count await expect(locator).toHaveCount(3);
beforeEach — avoiding repetition

When multiple tests in the same file need the same setup (navigating to a page, logging in, clearing state), you put that in a beforeEach hook. It runs automatically before every test in that describe block.

tests/specs/login.spec.ts In HireBoard
import { test, expect } from '@playwright/test'; test.describe('Login page', () => { // Runs before EVERY test in this describe block test.beforeEach(async ({ page }) => { // Clear localStorage so each test starts fresh await page.goto('/'); await page.evaluate(() => localStorage.clear()); await page.goto('/#/login'); }); test('employer lands on employer dashboard', async ({ page }) => { await page.getByTestId('email-input').fill('employer@test.com'); await page.getByTestId('password-input').fill('password123'); await page.getByTestId('login-submit').click(); await expect(page).toHaveURL(/employer\/dashboard/); await expect(page.getByTestId('nav-role-badge')).toHaveText('employer'); }); test('shows error for wrong password', async ({ page }) => { await page.getByTestId('email-input').fill('employer@test.com'); await page.getByTestId('password-input').fill('wrongpassword'); await page.getByTestId('login-submit').click(); await expect(page.getByTestId('login-error')).toBeVisible(); await expect(page.getByTestId('login-error')).toContainText('Invalid'); }); test('stays on login page when form is empty', async ({ page }) => { await page.getByTestId('login-submit').click(); // No redirect — still on login page await expect(page.getByTestId('login-page')).toBeVisible(); }); });
The problem POM solves

Imagine your login button changes its data-testid from login-submit to sign-in-btn. If that selector is copy-pasted into 15 test files, you update 15 files. With POM, you update it in one place — the Page class — and all 15 tests fix themselves.

POM also makes tests readable. await loginPage.login('user@test.com', 'pass') is far clearer than 4 lines of fill/click.

The POM mindset: A Page Object is a TypeScript class that represents one page (or component) of your app. It owns all the locators for that page and exposes high-level action methods. Tests use the class — they never touch raw selectors.
Generic POM structure
tests/pages/LoginPage.ts Generic pattern
import { Page, Locator } from '@playwright/test'; export class LoginPage { // All locators are properties of the class readonly emailInput: Locator; readonly passwordInput: Locator; readonly submitBtn: Locator; readonly errorMessage: Locator; constructor(private page: Page) { this.emailInput = page.getByTestId('email-input'); this.passwordInput = page.getByTestId('password-input'); this.submitBtn = page.getByTestId('login-submit'); this.errorMessage = page.getByTestId('login-error'); } // High-level action methods async goto() { await this.page.goto('/#/login'); } async login(email: string, password: string) { await this.emailInput.fill(email); await this.passwordInput.fill(password); await this.submitBtn.click(); } async getError(): Promise<string | null> { return this.errorMessage.textContent(); } } // Your test is now clean and readable: test('employer can log in', async ({ page }) => { const loginPage = new LoginPage(page); await loginPage.goto(); await loginPage.login('employer@test.com', 'password123'); await expect(page).toHaveURL(/employer\/dashboard/); });
Inheritance with BasePage — how HireBoard does it

When multiple pages share common elements (a navbar, a toast notification, a loading spinner), you extract those into a BasePage class that all other Page Objects extend. This is exactly what we built in HireBoard.

tests/pages/BasePage.ts → JobBoardPages.ts In HireBoard
// BasePage.ts — shared elements every page has export class BasePage { readonly navbar: Locator; readonly toast: Locator; readonly toastMessage: Locator; constructor(readonly page: Page) { this.navbar = page.getByTestId('navbar'); this.toast = page.getByTestId('toast'); this.toastMessage = page.getByTestId('toast-message'); } // Shared action all pages need async logout() { await this.page.getByTestId('logout-button').click(); } async getToastMessage() { await expect(this.toast.first()).toBeVisible(); return this.toastMessage.first().textContent(); } } // EmployerPage extends BasePage — inherits navbar + toast for free export class EmployerPage extends BasePage { readonly postJobButton: Locator; readonly statOpenJobs: Locator; constructor(page: Page) { super(page); // initialises BasePage locators this.postJobButton = page.getByTestId('post-job-button'); this.statOpenJobs = page.getByTestId('stat-open-jobs'); } async gotoDashboard() { await this.page.goto('/#/employer/dashboard'); } } // In a test: use BasePage methods AND EmployerPage methods together test('employer sees toast after posting job', async ({ page }) => { const employer = new EmployerPage(page); await employer.gotoDashboard(); await employer.postJobButton.click(); // ... fill form ... const msg = await employer.getToastMessage(); // from BasePage! expect(msg).toContain('Job posted'); });
What are fixtures and why do you need them?

A fixture is reusable setup and teardown logic that gets injected into your tests automatically. Playwright ships with built-in fixtures like page, browser, and context. But you can create your own.

The most common use case: authenticated pages. Instead of writing login steps in every single test, you create an employerPage fixture that logs in once and hands you a pre-authenticated page. Every test that needs an employer just asks for { employerPage }.

Think of fixtures like plugins for your tests. You declare what you need in the test parameters — { page }, { employerPage }, { applicantPage } — and Playwright sets it all up before your test runs, then tears it down after.
Generic fixture pattern
tests/fixtures/my.fixtures.ts Generic pattern
import { test as base, Page } from '@playwright/test'; // Define the shape of your custom fixtures type MyFixtures = { loggedInPage: Page; adminPage: Page; }; // Extend the base test with your fixtures export const test = base.extend<MyFixtures>({ loggedInPage: async ({ page }, use) => { // SETUP: runs before the test await page.goto('/login'); await page.getByTestId('email-input').fill('user@test.com'); await page.getByTestId('password-input').fill('pass123'); await page.getByTestId('submit').click(); await page.waitForURL(/dashboard/); // HANDOFF: give the test the ready page await use(page); // TEARDOWN: runs after the test (optional cleanup) await page.evaluate(() => localStorage.clear()); }, }); // Re-export expect so tests only need one import export { expect } from '@playwright/test'; // ───────────────────────────────────────────────────────── // In your test file — just import from your fixture file: import { test, expect } from '../fixtures/my.fixtures'; test('dashboard shows username', async ({ loggedInPage: page }) => { // page is already logged in — no setup needed! await expect(page.getByTestId('nav-user-name')).toBeVisible(); });
How HireBoard implements role-based fixtures

HireBoard has two roles — employer and applicant — each needing separate login state. We created a fixture for each so any test can ask for the role it needs in one line.

Why mock APIs in tests?

When you test against a real backend, your tests are only as reliable as the server. It might be slow, it might be down, or it might not have the exact data you need. API mocking lets you control what the server "returns" without a real server being involved at all.

Test error states the real API can't produce on demand Test loading states by adding artificial delays Verify the correct request body is being sent Block tracking/analytics calls from polluting tests
How it works: page.route(pattern, handler) intercepts any network request whose URL matches the pattern — before it leaves the browser. Your handler decides whether to fulfill it (return a fake response), continue it (let it through), or abort it (block it entirely).
The 4 essential mocking patterns
4 patterns you'll use constantly Generic patterns
// ── PATTERN 1: Return fake data ──────────────────────────────── await page.route('**/api/jobs', async route => { await route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify([{ id: '1', title: 'Mock Job' }]), }); }); // Use case: test how the UI renders with specific data shapes // ── PATTERN 2: Simulate a server error ───────────────────────── await page.route('**/api/applications', async route => { if (route.request().method() === 'POST') { await route.fulfill({ status: 500, body: 'Server error' }); } else { await route.continue(); // let GET through normally } }); // Use case: test your app's error handling UI // ── PATTERN 3: Add a delay (test loading states) ─────────────── await page.route('**/api/jobs', async route => { await new Promise(r => setTimeout(r, 2000)); // 2s delay await route.continue(); }); // Use case: verify a loading spinner appears before data loads // await expect(page.getByTestId('loading-skeleton')).toBeVisible(); // ── PATTERN 4: Inspect the outgoing request ──────────────────── let capturedBody: unknown; await page.route('**/api/applications', async route => { capturedBody = route.request().postDataJSON(); await route.fulfill({ status: 201, body: '{}' }); }); // Trigger the action... await page.getByTestId('submit-application').click(); // Then assert the correct data was sent: expect(capturedBody).toMatchObject({ jobId: 'job-1', coverLetter: 'Hello' });

Your practice challenges
Write these tests yourself in tests/specs/. Import from ../fixtures/auth.fixtures so you get the pre-logged-in pages. All locators are listed — your job is to write the test logic.
  • 🔍
    Search filters the job list correctly
    Goal: Navigate to /#/jobs as a guest. Type "UX" in the search box. Assert only jobs matching "UX" appear. Then clear the search and assert more results come back.

    Hint: Use allTextContents() on the title locator to get an array of all titles, then use expect(titles.every(t => t.includes('UX'))).toBeTruthy().

    Locators: getByTestId('search-input') · getByTestId('job-title') · getByTestId('jobs-empty')
  • 🔖
    Bookmark persists after page reload
    Goal: Login as applicant, bookmark job-1, then reload the page and verify the bookmark button still shows as bookmarked. This tests localStorage persistence.

    Hint: Use page.reload() then re-assert toHaveClass(/bookmarked/).

    Locators: getByTestId('bookmark-btn-job-1') · check for class /bookmarked/
  • 🚫
    Applicant cannot reach employer-only pages
    Goal: Login as applicant, directly navigate to /#/employer/dashboard, and assert you land on the unauthorized page — not the dashboard.

    Hint: Use the applicantPage fixture. This is a negative test — you're asserting something does NOT work.

    Locators: getByTestId('unauthorized-page') · getByTestId('employer-dashboard') (should NOT be visible)
  • 📝
    Employer posts a job and stat updates
    Goal: Login as employer, read the current "Open positions" stat, post a new job, go back to the dashboard, and assert the stat is now +1.

    Hint: Use parseInt(await page.getByTestId('stat-open-jobs').textContent() || '0') before and after.

    Locators: getByTestId('post-job-button') · getByTestId('job-title-input') · getByTestId('salary-min-input') · getByTestId('salary-max-input') · getByTestId('submit-job-button') · getByTestId('stat-open-jobs')
  • 📨
    Full apply flow — end to end
    Goal: Login as applicant, go to job-2's detail page, click Apply, fill the cover letter (50+ characters), attach the sample PDF, submit, assert the success toast, go to dashboard, assert the application appears with "Pending" status.

    Hint: For file upload: await page.getByTestId('resume-input').setInputFiles('tests/fixtures/files/sample-resume.pdf').

    Locators: getByTestId('apply-button') · getByTestId('cover-letter-input') · getByTestId('resume-input') · getByTestId('submit-application') · getByTestId('toast-message') · getByTestId('application-status-*')
  • 🔄
    Cross-role: applicant applies → employer reviews
    Goal: Use two separate browser contexts. In context 1 (applicant): apply to job-2. In context 2 (employer): navigate to job-2's applicants page and assert 1 application appears. This is the hardest challenge.

    Hint: Use const ctx = await browser.newContext() to create isolated sessions. Log in separately in each. Look at how permissions.spec.ts does the cross-role test at the bottom.

CI/CD — tests that run themselves

Continuous Integration (CI) means your tests run automatically every time code is pushed to GitHub — before it can merge. This catches bugs before they reach users, not after.

HireBoard already has this wired up. Every push to main triggers the GitHub Actions workflow in .github/workflows/playwright.yml. The pipeline installs dependencies, installs Playwright browsers, runs all tests, and uploads the HTML report as a downloadable artifact.

.github/workflows/playwright.yml In HireBoard
name: Playwright Tests on: push: branches: [main, develop] # runs on every push to these branches pull_request: branches: [main] # also runs when a PR is opened against main jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 # pull the code - uses: actions/setup-node@v4 # install Node.js with: node-version: 20 - run: npm ci # install dependencies - run: npx playwright install --with-deps # install browsers - run: npm test # run all tests - uses: actions/upload-artifact@v4 # save the HTML report if: always() # even if tests fail with: name: playwright-report path: playwright-report/ retention-days: 30
The key line is if: always() on the artifact upload. This ensures the test report is saved even when tests fail — which is exactly when you need it most.
Visual regression testing

Visual regression tests take a screenshot of a page or component and compare it pixel-by-pixel against a saved baseline image. If anything changes — a button moved 2px, a font colour changed, a layout broke — the test fails and shows you exactly what's different.

Visual snapshot testing — generic + HireBoard example Concept
// First run: creates baseline screenshots in tests/__snapshots__/ // Subsequent runs: compares against the baseline test('job listing page looks correct', async ({ page }) => { await page.goto('/#/jobs'); // Full page screenshot await expect(page).toHaveScreenshot('jobs-page.png'); }); test('job card component is visually stable', async ({ page }) => { await page.goto('/#/jobs'); // Just screenshot a single component, not the whole page const firstCard = page.locator('[data-testid^="job-card-"]').first(); await expect(firstCard).toHaveScreenshot('job-card.png', { maxDiffPixels: 50, // allow tiny antialiasing differences }); }); // Update baselines when you intentionally change the UI: // npx playwright test --update-snapshots
